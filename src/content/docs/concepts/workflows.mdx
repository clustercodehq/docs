A **Workflow** is a graph you draw. You place nodes — agent runs, loops,
prototypes, decisions, human approvals — connect them, and save the result as a
reusable definition. Firing it starts a **workflow run**, which walks the graph
one node at a time.

Where a [Run](/concepts/runs) is one agent doing one thing, and a
[Loop](/concepts/loops) is one agent iterating until a verifier agrees, a
workflow is the thing that puts several of those in a row and decides what
happens next based on how each one turned out.

<BetaAside feature="workflows">
Workflows is in beta. The core flow is solid, but the experience is still
evolving — expect changes as we refine it.
</BetaAside>

## The canvas

You build a workflow on a blank canvas. Drag on the nodes you need — Agent
Run, Loop and Prototype to do work; Decision and Human Approval to route —
and connect them with edges. A work node takes exactly one outgoing
connection; only a Decision or Approval fans out, one edge per labelled
branch it can produce (see [The five node kinds](#the-five-node-kinds) and
[How a Decision decides](#how-a-decision-decides) below). A connection can
also point backwards — drawn dashed and capped `⟲ max N` — so a
"review failed → fix → review again" cycle is expressible without running
forever (see [Bounded loop-backs](#bounded-loop-backs)). Save the graph as a
reusable definition; firing it starts a run.

## One run, one workspace

Every node in a single workflow run shares **one DevBox** and **one git branch**,
named `wf/<slug>/run-<n>`.

That is the whole point. The second node sees the files the first node wrote.
A decision can test the repository the run has been building. A loop can pick up
where an earlier run node left off. Without a shared workspace a graph of agents
is just a list of unrelated tasks.

The DevBox is created by the first node that needs one and handed down the graph
from there. You can also **pin** a workflow to an existing DevBox, in which case
every run works in that same persistent environment instead of a fresh one.

### One exception: a Prototype node

A bake-off exists so you can compare approaches, and comparing them in one
workspace would mean they overwrite each other. So a Prototype node forks: each
variant gets **its own DevBox** and **its own branch**, `proto/<node>/<engine>`,
taken from the run's branch — so every variant starts from the work the earlier
nodes did, not from an empty checkout.

When you promote a winner, its branch is fast-forwarded back onto
`wf/<slug>/run-<n>` and the run continues on the one branch it started with. The
divergence is temporary and always rejoins, so "one run, one branch" still holds
either side of a race.

## The five node kinds

Three kinds **do work**. Each one produces its own entity, with its own page you
can open and read exactly as if you had started it by hand. Two of the three run
unattended; a **Prototype also stops for you**, because picking the winner of a
bake-off is a judgement only a person can make.

| Node | What it does | Produces |
|---|---|---|
| **Agent Run** | One autonomous agent run against a prompt | a [Run](/concepts/runs) |
| **Loop** | Iterates until an independent verifier approves | a [Loop](/concepts/loops) |
| **Prototype** | Races several engine+model variants on one brief, each in its own DevBox and branch, then **waits for you to pick a winner** | a [Prototype](/concepts/prototyping) |

Two kinds **route**. They do no work themselves; they decide where the run goes
next.

| Node | What it does |
|---|---|
| **Decision** | Picks a branch from the previous node's result |
| **Human Approval** | Stops and waits for a person, then takes their answer's branch |

#### Which kinds stop for a person

**Two, not one.** Human Approval is the obvious one. A **Prototype** is the
other: the race finishing is not the node finishing. A prototype node is an
approval node that does work first — it holds the run until you promote a
variant, and if the answer window lapses with nothing promoted the node fails
rather than guessing. There is no default winner, because "which approach is
better" is the one question the platform cannot answer for you.

### One exit, unless it routes

An Agent Run, a Loop and a Prototype each take **exactly one** outgoing
connection. Only Decision and Approval nodes fan out, onto as many labelled
branches as you draw.

This is enforced while you draw: once a work node has its one exit, its
connection points dim and refuse a second. To split a path, put a Decision or an
Approval in between. That constraint is what keeps a graph readable — every fork
is an explicit, labelled, inspectable choice rather than an implicit one.

### How a Decision decides

A Decision node picks its branch using one of three **evaluators**:

- **Status** — routes on the previous node's own result. No extra work, no
  agent, no cost.
- **Command** — runs a command inside the run's shared DevBox. Exit code `0`
  takes the `pass` branch; anything else takes `fail`. This is how you route on
  "do the tests actually pass", not on what an agent claims.
- **Agent** — asks an agent to judge, and offers your branch labels as the only
  answers it may give.

<Aside type="caution" title="Command and Agent decisions need a workspace">
A Command or Agent decision runs *inside* the run's DevBox, and only an Agent Run
or a Loop node hands one over — a Prototype's variants each keep their own. If
you draw a Command or Agent decision that could be reached before any run or loop
has gone first, the workflow refuses to save and tells you so. Put a run or loop
before it, or pin the workflow to an existing DevBox.
</Aside>

## Routing vocabularies

A **Status** decision offers the branch labels that its predecessor can actually
produce — and those differ by node kind, because the three kinds have genuinely
different outcomes. The canvas offers you the right set as one-click chips; you
never have to remember them.

| Predecessor | Branch labels it can produce |
|---|---|
| **Agent Run** | `completed` · `failed` · `skipped` · `stopped` |
| **Loop** | `verified` · `needs_owner` · `budget_exhausted` · `no_progress` · `circuit_broken` · `error` · `user_cancelled` |
| **Prototype** | `completed` · `failed` · `cancelled` · `archived` |

A loop's labels are its **stop reasons**, because a loop has no other verdict to
report — "why did you stop" *is* its outcome. That is what makes
`verified → ship`, `no_progress → ask a human` expressible as a graph.

Every routing node also accepts a **`default`** branch, which catches anything
the other labels did not match. If a result matches no branch and there is no
`default`, the run fails rather than quietly stopping — a graph that silently
does nothing is worse than one that tells you it has a hole.

## Bounded loop-backs

A connection may point **backwards**, which is how "review failed → fix →
review again" is expressible without a separate construct. A backwards
connection is drawn dashed and carries a cap: **`⟲ max N`**.

The cap is what makes it finite. When a back-edge has been traversed N times the
run stops with `back_edge_exhausted` rather than cycling forever. If you want
something better than a failure at the end of the rope, wire an explicit
give-up branch off the decision — for example a Human Approval that asks you
whether to keep going.

A node re-entered by a back-edge shows a **×N** badge in the run trace, so you
can see at a glance which parts of the graph the run went around more than once.

## What a run looks like

Firing a workflow **snapshots** its definition. Editing the workflow afterwards
never changes a run that is already in flight, and never rewrites the history of
one that has finished — a run is a record of what was actually executed.

The run page shows the graph with each node coloured by status alongside an
**execution order** timeline: one row per node attempt, with its kind, duration
and cost, and a link straight into the entity that node produced. Costs roll up
from those entities to the run total, so a workflow's price is the real sum of
the work it did.

The definition page keeps the full **run history** for that workflow, and while
one is in flight it carries a live banner through to it.

## Watching a run

A firing walks the graph **one node at a time**, all of it in the run's one
shared DevBox on its one branch — the same workspace every node before it has
been writing to. Open the run and you watch that walk happen: each node lights
up as it starts, and finishes into whichever status its kind can produce
before the run moves to whatever the graph says comes next.

If the graph carries a **Human Approval** node, the run stops there and waits
— its status parks until someone answers, however long that takes — then
resumes down whichever branch the answer selects.

## Scheduling a workflow

A [Schedule](/concepts/schedules) can fire a workflow the same way it fires a
run — on a cron expression, or on an interval. The schedule references the
workflow by id, so it always fires the current saved definition.

## Workflow Library

Drawing a graph from an empty canvas is the slow way to start. The
**Workflow Library** is a docked panel on the Workflows page — titled
"Workflow Library", collapsed by default — with 11 curated graphs for common
shapes: an issue taken all the way to a merge-ready PR, a tournament between
two competing approaches, a progressive rollout with auto-rollback. Picking
one is different from the Loop Library: **Use** navigates you
away, to `/workflows/new?template=<id>`, and opens the graph editor there
already populated — every node, every labelled edge, every capped back-edge,
laid out and ready to read. As with the Loop Library, the host axis is left
blank — worker, DevBox, image, repository travel with your account, not the
template — so you always fill those in before you can save and fire it.

{/* SCREENSHOT: workflow-library — the docked Workflow Library panel on the Workflows page, showing template cards with tags, a Details toggle and a Use button */}

| Template | What it does |
|---|---|
| **Hello, workflow** | A read-only tour of your repository, then a branch on how it went — the smallest graph that is still a workflow. |
| **Fix until green** | Do the work, re-check, loop back on failure up to three times, then ask a human before shipping. |
| **Issue → agent review → your approval** | One agent implements a fix, a fresh agent reviews the diff against the issue, and you approve the resulting PR. |
| **Tight loop** | Build and test in one node, gate on the real test command, loop back until it exits 0. |
| **Triage router** | Reads an issue once, classifies what it really is, then hands it to the right downstream handler. |
| **Adversarial verification** | One agent builds it, a fresh agent tries to refute it, and the verdict decides whether to redo the work. |
| **Tournament of approaches** | Two candidate implementations on two branches, judged head-to-head by an agent decision, winner shipped. |
| **Progressive rollout with auto-rollback** | Builds, gates on tests, deploys behind a flag, raises traffic in steps, and rolls back automatically when health drops. |
| **Closed observability loop** | Ships the change, watches production for anomalies over a real observation window, and feeds what the telemetry says back into the fix. |
| **The SDLC, drawn as a graph** | The whole lifecycle as ten explicit nodes, using every node kind, with both its review and monitoring cycles drawn and capped. |
| **Issue in, merge-ready PR out** | Sixteen nodes, two capped loops, exactly one human gate — the graph translation of ClusterCode's own autonomous delivery skill. |

## Availability

Workflows is available on **every plan**, including Free.

The plan limit is on **concurrently active workflow runs**, not on how many
workflows you have drawn. Saving definitions is unlimited on every plan; what a
higher plan buys you is more of them running at the same time.
