## Usage

```bash
clustercode config <subcommand> [arguments]
```

## Subcommands

### `set`

Set a configuration value:

```bash
clustercode config set WORKER_NAME my-dev-machine
```

### `get`

Read a configuration value:

```bash
clustercode config get WORKER_NAME
```

### `list`

Show all configuration values:

```bash
clustercode config list
```

## Allowed Keys

| Key | Description |
|-----|-------------|
| `WORKER_NAME` | Display name for this worker (max 64 characters) |
| `RUNTIME_MEMORY_MB` | Memory, in MiB (1024-based), to give the container runtime. `8192` is 8 GiB. The `MB` in the key name is historical. |
| `RUNTIME_RECLAIM_VERIFIED` | `yes` or `no` — whether the WSL2 VM has been measured actually returning memory to Windows on this machine. |

Only the keys listed above are accepted. Attempting to set an unknown key returns an error.

### `RUNTIME_MEMORY_MB`

```bash
clustercode config set RUNTIME_MEMORY_MB 24576
```

Must be a whole number, at least 2048, and no more than a per-machine safe
ceiling (host RAM minus an OS reserve — the CLI reports the exact limit if
you go over it). Values are in MiB (1024-based) — `8192` is 8 GiB. The `MB`
in the key name is historical; the CLI displays GiB throughout.

2048 is a hard floor, not a usable recommendation — it cannot host even one
default 4 GiB DevBox once the host reserve is subtracted. Hosting one needs
roughly 6 GiB.

`onboard` writes this key itself after a successful apply, recording the value
it applied. That stored value is what makes `doctor` stop suggesting a
different size: a measured runtime within about 7% of it counts as "the size
you asked for" — the guest kernel keeps some of what's allocated, so an exact
match never happens — and is left alone instead of being re-litigated on every
run.

Setting this key by itself doesn't move any memory around — it takes effect
the next time a container-runtime machine is created, or the next time you
run [`clustercode onboard`](/cli/onboard), which is also where the interactive
sizing prompts and the platform-specific apply steps (including the Windows
`.wslconfig` / `wsl --shutdown` behavior) live. See
[Sizing container runtime memory](/self-hosting/runtime-memory) for the full
guide.

### `RUNTIME_RECLAIM_VERIFIED`

```bash
clustercode config set RUNTIME_RECLAIM_VERIFIED yes
```

Accepts `yes` or `no`; anything else is rejected with
`Reclaim verification must be yes or no (or run clustercode onboard --verify-reclaim to measure it)`.

On Windows, the WSL2 VM only returns memory to the host when
`[experimental] autoMemoryReclaim` is set — and even then, only if the build
honours it. The setting is a request, and it has been observed accepted and
completely inert. So the CLI sizes the runtime optimistically for exactly one
state: reclaim **measured** working on this machine. This key is that
measurement.

Normally you don't set it by hand:
[`clustercode onboard --verify-reclaim`](/cli/onboard#verifying-that-memory-reclaim-works)
runs the experiment and records the answer. Set it yourself when you've
[measured it manually](/self-hosting/runtime-memory#measuring-it-by-hand)
instead.

A verdict is only meaningful next to the WSL build it describes, so it's stored
alongside a companion `RUNTIME_RECLAIM_VERIFIED_WSL` stamp, which
`clustercode config list` shows and `config set` does **not** accept — the CLI
writes it for you, whichever way the verdict was recorded. When the running WSL
version stops matching the stamp, the verdict is treated as unanswered rather
than carried forward: the CLI goes back to sizing as if reclaim doesn't work,
and asks again. That's deliberate — this behaviour is a property of the WSL
build, and an upgrade can fix it or break it.

Clearing the key (or losing the stamp) is safe in the same direction: with no
usable verdict, the runtime is sized as though reclaim does nothing.

## Configuration File

Location: `~/.clustercode/config.json`

```json
{
  "WORKER_NAME": "my-dev-machine",
  "RUNTIME_MEMORY_MB": "24576",
  "RUNTIME_RECLAIM_VERIFIED": "no",
  "RUNTIME_RECLAIM_VERIFIED_WSL": "2.7.13.0"
}
```
