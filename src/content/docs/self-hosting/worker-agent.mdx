The worker agent is a lightweight, standalone binary that runs on each machine and executes DevBoxes on behalf of the orchestrator. It has no runtime dependencies — the `clustercode` CLI downloads and runs it for you.

## How it connects

```
Orchestrator (cloud)
    ▲
    │  outbound WebSocket
    ▼
Worker agent (your machine)
    │
    ▼
Podman / Docker containers
```

The agent connects **outbound** to the orchestrator over an authenticated connection — no inbound ports, no port forwarding, no static IP or DNS on the worker side. It works behind NAT and firewalls that allow outbound HTTPS.

Once connected, the agent runs DevBox operations locally (create, start, stop, terminal, and so on) as the orchestrator requests them.

## Resilience

- If the connection drops, the agent reconnects automatically.
- DevBoxes keep running while the agent is disconnected — they aren't affected by the agent's connection state.
- The agent is safe to restart; it picks up existing DevBoxes when it reconnects.

## Live terminals

Terminal and display output from a DevBox streams back through the agent to your browser, giving you a live web terminal for each DevBox.

## Disk hygiene

Image builds leave things behind: images a rebuild replaced, the intermediate
layers of a build that failed, and — inside the Podman machine on Windows —
scratch directories and logs that no Podman command shows. The agent cleans
these up, under the rules below.

### Images it replaced or failed to build

On the worker's container engine (Podman or Docker), the agent removes images
left behind by:

- a **failed image build** — only intermediate images that carry that build's
  ID;
- a **rebuild** that replaces an image, or a
  [snapshot of a DevBox](/guides/build-image-from-container) that replaces one
  — only the image it has just replaced.

Even then, an image is removed only when it has **no name** (no tag or
digest), **no child images**, and **no container** using it. The agent then
works up through that image's parent layers, removing each one only while it
is unnamed, has no other child, and is unused. It stops at the first layer
that is named (a base image such as `ubuntu:24.04`, for example), shared with
another image, or in use, and after at most 64 layers.

### Inside the Podman machine (Windows)

When the worker's container runtime is a local Podman machine on WSL2 — the
setup [`clustercode onboard`](/cli/onboard) creates on Windows — the agent also
looks after the machine itself:

- **Journal size.** If no `SystemMaxUse=` is set anywhere in the machine's
  journald configuration (every configuration directory, drop-ins included),
  the agent writes its own drop-in,
  `/etc/systemd/journald.conf.d/00-clustercode-journal-cap.conf`, containing
  `SystemMaxUse=256M`, and restarts journald once. It logs
  `guest clean: capped the podman machine's journal` with the drop-in's path.
  It never edits `/etc/systemd/journald.conf`, and if it can't read journald's
  configuration it does nothing.

  A `SystemMaxUse=` you've already set, in any journald configuration file, is
  left alone. Once the agent's drop-in exists, drop-ins take precedence over
  the main file, so set your own limit in a drop-in whose name sorts after the
  agent's (for example `50-journal-size.conf`). Deleting the agent's file
  removes its cap; unless you've set your own limit or turned the cleanup off
  (below), the agent writes it again the next time it starts.

  Containers that use the journald log driver keep their logs in the journal,
  so the cap also limits how much of their log history is kept.
- **Leftover build scratch.** A build that is interrupted can leave a large
  temporary directory behind in the machine — invisible to `podman system df`
  and untouched by `podman system prune`. Every 15 minutes (the first run is
  about 2 minutes after the worker starts), the agent removes directories in
  the machine's `/var/tmp` named `buildah` followed by digits, or
  `clustercode-commit.XXXXXXXX` (left by a DevBox snapshot), that are older
  than the scratch age (**3 hours** by default). It removes them only when no
  build is running in the machine and nothing is using the directory. If it
  can't check for running builds, it skips that run and logs
  `guest clean: could not check for running builds or in-use scratch in the podman machine; skipping scratch reap`.
  If a build-like process keeps it waiting for longer than the scratch age, it
  logs
  `guest clean: scratch reap has been paused by a build-like process in the podman machine for longer than the scratch age`
  once.

What it will **never** do:

- Prune, force a removal, or remove all images. Your own images and
  containers are never touched, and a layer one of your images builds on is
  kept.
- Remove stopped DevBoxes. A stopped DevBox keeps its disk until you remove
  it — review and remove the ones you no longer need in the console's
  [Fleet Cleaner](https://console.clustercode.io/fleet/cleaner).

To turn the in-machine cleanup off, or change the scratch age, set these in
the environment you start `clustercode worker` from (the CLI passes its
environment on to the agent):

| Variable | Default | Effect |
|----------|---------|--------|
| `WORKER_GUEST_CLEAN` | on | Set to `off` to stop capping the machine's journal and removing leftover build scratch |
| `WORKER_GUEST_CLEAN_SCRATCH_AGE_HOURS` | `3` | How old, in hours (1–168), leftover build scratch must be before it's removed |

```powershell
$env:WORKER_GUEST_CLEAN = "off"
clustercode worker
```

Turning the cleanup off doesn't remove a journal drop-in the agent has already
written; delete that file yourself if you don't want the cap.

<Aside type="note" title="This doesn't shrink the disk file on Windows">
  Cleanup frees space *inside* the machine, which slows how fast its virtual
  disk grows. On Windows that disk file never shrinks by itself, so space it
  has already taken stays taken until you run
  [`clustercode machine compact`](/cli/machine). `clustercode doctor` tells
  you when that's worth doing.
</Aside>

## Running it

Start the worker with the CLI:

```bash
clustercode worker
```

Leave it running to keep the machine online as a worker. See [Register a Worker](/getting-started/register-worker) to get set up, and [`clustercode doctor`](/cli/doctor) to check its health.
