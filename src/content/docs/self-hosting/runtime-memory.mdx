How much memory your container runtime can use determines how many DevBoxes —
and what size — this worker can host at once. This page covers how that
memory is sized, how to change it, and the platform differences you need to
know before you do.

## Why this matters

The scheduler gives DevBoxes to workers based on capacity it can actually use.
On macOS and Windows, Podman (and Docker) run inside a VM, and that VM's
memory ceiling — not the host's total RAM — is what limits this worker. A
worker whose runtime can only see a couple of GiB will silently fit fewer
DevBoxes than the host's RAM suggests it should.

Check your current numbers with:

```bash
clustercode doctor
```

which reports the [runtime-memory check](/cli/doctor#runtime-memory) — engine
memory against host RAM and an estimated DevBox capacity.

Values you configure — [`RUNTIME_MEMORY_MB`](/cli/config#runtime_memory_mb)
and `onboard`'s `--memory <mb>` — are in MiB (1024-based): `8192` means 8 GiB.
The `MB` in the names is historical; everywhere the CLI *displays* memory, it
shows GiB.

## Dedicated worker vs. shared machine

[`clustercode onboard`](/cli/onboard) asks how this machine is used and offers
a preset for each:

| Use | The runtime gets | Host keeps, with memory reclaim **verified** | Host keeps, otherwise |
|---|---|---|---|
| **Dedicated worker** — mostly hosts DevBoxes | Everything except the host's reserve | 6 GiB | `max(8 GiB, 25% of RAM)` |
| **Shared** — you also work on this machine day to day | At most half the machine | 12 GiB | 12 GiB |

Linux has no VM in the way — the container runtime *is* the host, so there's
nothing to reserve or size separately.

The larger reserve on a shared machine exists so the desktop stays usable
while DevBoxes are running; a dedicated worker doesn't need that headroom, so
it can give away nearly everything.

The two right-hand columns are the important part. A reserve is only real if
something makes the VM give memory back — otherwise the host "keeps" a number
that the VM slowly eats. And *writing* the reclaim setting is not the same as
the VM honouring it: the setting is a request, and it has been measured
accepted and completely inert. So the smaller *Dedicated* reserve of 6 GiB
applies on exactly one condition — reclaim has been **measured** to work on
this machine, with
[`clustercode onboard --verify-reclaim`](#verifying-it-works-on-your-machine)
or by hand. Until then, the VM is assumed fully inflated and the *Dedicated*
preset leaves `max(8 GiB, 25% of RAM)` behind instead. The same applies
everywhere reclaim cannot exist at all (macOS, Hyper-V, WSL builds older than
2.0), and always to Docker: the CLI cannot measure Docker's VM, so a Docker
runtime is sized as if reclaim does not work even when reclaim is on.
The *Shared* reserve is already sized for a machine somebody works on, so it
doesn't move.

On a 31.6 GiB Windows host that's a *Dedicated* preset of 25 GiB once reclaim
is verified, and 23 GiB until it is.

## It's a ceiling, not a reservation

The number you configure caps what the container runtime **can** take — it
isn't set aside up front. But "not set aside up front" is not the same as
"given back," and that distinction is what decides whether the reserve in the
table above actually protects your machine:

- **Windows** — the WSL2 VM returns memory to Windows only while *memory
  reclaim* is on (`[experimental] autoMemoryReclaim` in `.wslconfig`, WSL 2.0
  or newer; from WSL 2.5.10 it's on unless you set it to `disabled`). With it
  off the VM keeps everything it has ever touched — including the guest file
  cache left behind by image pulls and builds — until `wsl --shutdown`. And
  reclaim is a request the build is free to ignore, so treat the ceiling as
  fully used until you have
  [measured otherwise](#verifying-it-works-on-your-machine).
- **macOS** — the VM does not return memory to the host until it restarts.
  Treat the ceiling as fully used.

So size for the number you are willing to have the machine hold *permanently*,
not for the peak you expect. Where reclaim is enabled **and working** the VM
hovers near its working set and only approaches the ceiling under load;
otherwise the ceiling behaves like a floor the VM climbs to and stays at.

## Hard ceilings

### The ceiling and the floor

There are **two different reserves** on this page, and they are not the same
number. Keeping them apart matters on Windows, where they differ:

| | Windows | macOS | Linux |
|---|---|---|---|
| **Preset reserve** — what *Dedicated* leaves behind, with memory reclaim **verified** | 6 GiB | — | none |
| **Preset reserve** — what *Dedicated* leaves behind, otherwise | `max(8 GiB, 25% of RAM)` | `max(8 GiB, 25% of RAM)` | none |
| **Preset reserve** — what *Shared* leaves behind | 12 GiB | 12 GiB | none |
| **Hard OS reserve** — the most any value may take | 4 GiB | 6 GiB | none (no VM) |

The preset reserves are conservative defaults chosen so the machine stays
comfortable. The hard OS reserve is the absolute limit: `RUNTIME_MEMORY_MB` can
never exceed host RAM minus that figure, whatever you type.

macOS has no reclaim setting at all, so its *Dedicated* preset is always the
no-reclaim one.

So on a 32 GiB Windows host with reclaim **verified**, the *Dedicated* preset
offers 26 GiB (leaving exactly 6). Until it is verified — including while
reclaim is on and simply unchecked — the preset offers 24 GiB (leaving 8),
because a machine sized on an unverified promise is a machine sized wrong. A
custom value may go as high as 28 GiB (leaving exactly 4) either way — but on
a machine that never gives memory back, 28 GiB is what the VM will eventually
be holding.

[`clustercode config set RUNTIME_MEMORY_MB`](/cli/config#runtime_memory_mb)
and the `onboard` prompts both enforce this — a value above the ceiling is
rejected with the exact limit for your machine, not silently clamped.

At the other end, 2048 MiB is a hard floor, not a usable recommendation — a
value that low cannot host even one default-sized (4 GiB) DevBox once the
host reserve is subtracted. Hosting one needs roughly 6 GiB.

## Memory reclaim on Windows

WSL2 sizes its VM with a balloon that only ever inflates. `[wsl2] memory=` is
the ceiling on that balloon, and only memory reclaim deflates it. One key in
`%UserProfile%\.wslconfig` controls it:

```ini
[experimental]
autoMemoryReclaim=gradual
```

WSL accepts three values, in any letter case:

- **`dropCache`** — drops the guest's page cache once the VM goes idle. This is
  WSL's default: from WSL 2.5.10, a `.wslconfig` without the key — or with it
  commented out, in another section, or set to a value WSL doesn't recognise —
  gets `dropCache`.
- **`gradual`** — returns memory a little at a time while the VM is idle, and
  Microsoft's recommended setting.
- **`disabled`** — the only value that turns reclaim off.

The CLI reads the file the way WSL does: a missing or unrecognised value is
WSL's default, so reclaim counts as on, and only `disabled` counts as off. The
exception is WSL 2.0 up to 2.5.10, whose default the CLI can't confirm — there
a missing or unrecognised value counts as off. Builds older than 2.0 ignore the
key altogether.

Where reclaim is off, `clustercode onboard` writes the entry above, alongside
`[wsl2] memory=` — one read, one backup, one write, whether the allocation is
changing too. It never writes over a mode that is already in effect, whether
you set it or WSL's default did. Your existing comments, blank lines, unrelated
keys and unrelated sections survive verbatim, and the first write keeps a
`.wslconfig.bak` copy. Like any `.wslconfig` change it takes effect on the
next `wsl --shutdown`, which `onboard` runs for you after asking. That command
stops every WSL distribution on the machine, not only Podman's.

Reclaim that is on — `gradual` or `dropCache`, set by you or by default —
counts as *configured*. That is not treated as reclaim that works: see the next
section for why.

### Five states, not two

Whether the VM gives memory back is a property of your Windows build, not of
your config file, so the CLI keeps configuration and behaviour apart:

| State | What it means | What the runtime is sized for |
|---|---|---|
| **Off** | `autoMemoryReclaim=disabled` — or, on WSL 2.0 up to 2.5.10, no value WSL recognises | A VM that never gives memory back |
| **Unsupported** | Your WSL predates 2.0, or its version can't be read | A VM that never gives memory back |
| **Configured** | Reclaim is on, set by you or by WSL's default; nobody has measured it | A VM that never gives memory back |
| **Verified** | Measured, on this machine, against this WSL build and reclaim mode: memory comes back | The 6 GiB *Dedicated* reserve |
| **Inert** | Measured, and this build returns nothing | A VM that never gives memory back |

Only **verified** buys the smaller reserve. Everything else is sized as if
reclaim does not exist, which is deliberately the safe direction to be wrong
in. Each state has its own `doctor` wording — see
[Memory reclaim](/cli/doctor#memory-reclaim-windows-wsl-backend).

Only a Podman machine on the WSL backend can reach **verified** or **inert**,
because that is the only VM the CLI can measure. Docker on the WSL backend
stops at *configured*: its VM cannot be measured from the CLI, so Docker is
always sized as if reclaim does not work, and the lever is its size — lower
`[wsl2] memory=` in `.wslconfig`. (On Docker Desktop's Hyper-V backend there is
no reclaim setting at all; lower the memory in Docker Desktop's settings.) A
runtime whose backend the CLI cannot identify can't get past *configured* either.

A verdict is stored together with the WSL version and the reclaim mode
(`gradual` or `dropcache`) it was measured under — the mode in effect, so a
machine that never sets the key is stamped `dropcache`. If either changes — a WSL
upgrade, or switching modes — the old answer is not carried forward: the status
goes back to *configured* and the runtime is sized as if reclaim does not work.
That's right, because this behaviour has changed between builds. Nothing re-runs
the measurement for you. `doctor` suggests
`clustercode onboard --verify-reclaim` again, and if the size you stored earlier
is now above the ceiling for an unverified host, the next `clustercode onboard`
warns about it:

```
25600MB is above the 23552MB ceiling for this machine while memory reclaim is not verified, so the runtime can hold on to memory Windows needs.
```

and, in a terminal, asks what to do: verify now, lower the runtime to the ceiling, or keep the
size you have.

### Checking whether it's on

```bash
clustercode doctor
```

The [runtime-memory check](/cli/doctor#runtime-memory) appends what it found to
its line. With reclaim off it warns:

```
memory reclaim is off, so the runtime keeps memory the host may need
```

With reclaim on but never measured — including a machine that never sets the
key — what you get depends on the size.
If the runtime is already within what a host without reclaim can afford, the
check passes and notes the open question:

```
(memory reclaim configured but unverified — `clustercode onboard --verify-reclaim`)
```

If the runtime is larger than that, it is sized on a promise nobody has checked,
so the check warns and offers both ways out:

```
memory reclaim is configured but unverified, and the runtime is sized as if it works; verify with `clustercode onboard --verify-reclaim` or lower to `clustercode onboard --memory 23552`
```

With Docker, which can't be verified, the same two cases read
`(memory reclaim configured but not verifiable for Docker)` and
`memory reclaim is configured but cannot be verified for Docker, so size as if it does not work; lower [wsl2] memory= to 23552MB`.

The [host-memory check](/cli/doctor#host-memory) on the next line tells you what
Windows actually has left. Running `clustercode onboard` on a machine whose size
is already correct still offers to turn reclaim on where it's off, with no
resize.

### Verifying it works on your machine

Reclaim only runs while the guest is idle, so it isn't instantaneous — and on
some builds it never happens at all, however the file is written. The CLI can
measure it for you:

```bash
clustercode onboard --verify-reclaim
```

What that does: it reads back up to 4 GiB of the container runtime's *existing*
image data to load the VM's page cache — reading, never writing, so it consumes
no disk — then leaves the machine completely alone and watches the VM from the
Windows side for up to twelve minutes. It samples only from Windows, because
any command into the guest resets the idleness reclaim is waiting for.

A shrinking VM is not enough for a *yes*. Windows also trims a VM's memory on
its own when it runs short, and that looks like reclaim from the outside. So
the measurement only counts memory that **Windows actually got back**, held
for a sustained stretch, and it checks afterwards that the guest really did
release its cache.

Before it measures anything, it checks that the answer would mean something.
It runs only when:

- the runtime is **Podman on the WSL backend** — Docker's VM can't be measured
  from the CLI, and a Hyper-V backend has no reclaim setting;
- memory reclaim is **on** (not `disabled`, and `.wslconfig` can be read), and
  the WSL version can be read so the result can be tied to it;
- no **ClusterCode worker** is running on this machine (see below);
- the runtime memory step of `onboard` **completed**, so there is a settled
  runtime to measure;
- the runtime is **idle** — with containers running it stops immediately with
  `Containers are running, so the runtime never goes idle. Stop them and try
  again.`

Otherwise it says why and records nothing. Budget for 10 minutes or more, as
the prompt says: loading the cache comes before the idle watch, so on a slow
disk a run can take well over twelve minutes.

`onboard` also offers the same measurement, unprompted, at the one moment the
answer matters most — right after it has turned reclaim on:

```
Verify that memory reclaim works on this machine now? Takes 10 minutes or more; the runtime must stay idle.
```

There are **three** outcomes, not two:

- **Yes** — `Memory reclaim works here: the VM gave back 3.4 GiB while idle,
  and Windows got 3.1 GiB of it back.` The verdict is recorded, and when
  `onboard` offered the measurement it then offers to raise the runtime to the
  size a verified host has earned (`Reclaim verified — raise the runtime to
  25 GiB?`).
- **No** — `Memory reclaim did not return memory on this machine: the VM still
  holds 16.3 GiB after idling. The runtime will be sized as if reclaim does not
  work.` The verdict is recorded, and when `onboard` offered the measurement it
  tells you the ceiling that follows from it: `Sized as if reclaim does not
  work, the ceiling for this machine is 23552MB.`
- **Inconclusive** — the run couldn't establish either answer, and says why.
  Typical reasons: containers were running; a ClusterCode worker was running,
  or started during the run; the VM wasn't up, or restarted
  during the run; Windows itself ran short of memory, which shrinks the VM
  whether or not reclaim works; `.wslconfig` changed after the VM started, so
  it hasn't loaded the setting yet (the message tells you to run
  `wsl --shutdown`, which stops every WSL distribution, then
  `podman machine start`); or there simply wasn't enough existing data to pull
  through the cache
  (`Could not load the VM's cache: the runtime has only 210 MiB of cacheable
  data and headroom, which is too little to measure reclaim against.`). Nothing
  is recorded — "we couldn't tell" is not evidence for either answer — so the
  runtime stays sized conservatively and you can re-run once the cause is gone
  or the runtime has pulled a few images. The same goes for a run during which
  the WSL version or the reclaim mode changed.

The result is stored as
[`RUNTIME_RECLAIM_VERIFIED`](/cli/config#runtime_reclaim_verified), stamped with
the WSL version and the reclaim mode it was measured under.

A worker running on the same machine keeps the runtime busy, so the VM never
goes idle, and it can
[drop the VM's cache itself](#the-worker-drops-the-cache-itself) — which from
Windows looks just like reclaim at work. So the run won't start while a
ClusterCode worker process is running on this machine, which it checks with
`tasklist`:

```
A ClusterCode worker is running on this machine. It keeps the runtime busy and drops the VM's cache when Windows runs low on memory, either of which would skew the result. Stop the worker and try again.
```

It checks again after every sample of the idle watch and once more before
giving an answer. A worker that has appeared by then makes the run
inconclusive (`Reclaim could not be measured: a ClusterCode worker started
during the measurement, and a worker keeps the runtime busy and drops the VM's
cache when Windows runs low on memory. Stop the worker and try again.`). If the
process list can't be read, the run doesn't guess: at the start it measures
nothing (`Could not list the running processes (tasklist) to check that no
ClusterCode worker is running, so nothing was measured. Try again.`), and later
it records nothing (`Reclaim could not be measured: the running processes could
not be listed (tasklist) to check that no ClusterCode worker started during the
measurement. Nothing was recorded.`). A worker that starts and exits entirely
between two samples, about 30 seconds apart, isn't seen.

#### Measuring it by hand

The same experiment, if you'd rather run it yourself:

1. Give the VM some cache to hold — pull an image or run a build.
2. Note `vmmem` (or `vmmemWSL`) in Task Manager's Details tab, and the amount
   of available memory on the Performance tab.
3. Leave the machine idle for 10–15 minutes with no DevBoxes and no worker
   running. Keep
   Windows comfortably above 4 GiB available the whole time: below that,
   Windows trims the VM on its own, and so does the
   [worker's cache drop](#the-worker-drops-the-cache-itself) — neither is
   reclaim.
4. Watch `vmmem` shrink **and** Windows' available memory rise by a comparable
   amount. A VM that shrinks while Windows gains nothing is not a *yes*.

Then record what you found, so the sizing matches reality:

```bash
clustercode config set RUNTIME_RECLAIM_VERIFIED yes   # or: no
```

The CLI stamps the verdict with the running WSL version and the reclaim mode in
effect (`dropcache` where the key isn't set), and confirms both:

```
Set RUNTIME_RECLAIM_VERIFIED = yes (WSL 2.7.13.0, autoMemoryReclaim=gradual)
```

It refuses, records nothing and exits with an error when there is nothing
the verdict could describe: off Windows, when `wsl --version` can't be read,
when memory reclaim is off, or when `.wslconfig` can't be read.

Don't assume the answer. On a Windows 10 21H1 machine with WSL 2.7.13, neither
mode returned any of ~9 GB of cache in 16 minutes idle, while dropping the
cache by hand returned ~10 GB in 20 seconds — the setting can be present and
inert. If `vmmem` stays flat through a long idle window, that's your host: use
the fallbacks in
[Windows becomes slow or hangs while the worker runs](/self-hosting/troubleshooting#windows-becomes-slow-or-hangs-while-the-worker-runs).

`onboard` does **not** write this setting for Docker Desktop's WSL2 backend,
the same way it doesn't write `memory=` there. From WSL 2.5.10 reclaim is on
there too unless the key says `disabled`; you can set the `[experimental]` key
yourself and apply it with `wsl --shutdown` (which stops every WSL
distribution), but don't size on it: the CLI can't measure Docker's VM, so it
always treats Docker as a VM that keeps what it takes. The lever that protects
the host is a smaller `[wsl2] memory=`. Hyper-V backends don't read
`.wslconfig` at all and have no equivalent setting; lower the memory in Docker
Desktop's settings instead.

### The worker drops the cache itself

Memory reclaim is WSL's mechanism, and on some builds it does nothing. The
worker doesn't rely on it. When the container engine is a local Podman machine
on the WSL backend — and the worker has verified that it is — it watches how
much memory Windows has available. When that falls below a floor, 4 GiB by
default, it frees the Podman machine's page cache from inside the VM:

```bash
sync && echo 1 > /proc/sys/vm/drop_caches
```

`sync` first, so recently written data becomes droppable; then `1`, which frees
the page cache and nothing else. That is where the memory held by image pulls
and builds lives. It never touches memory a program is using, and never
touches images, containers or volumes: a running DevBox loses cache warmth,
not data. Windows typically reflects the freed memory within about 20 seconds.

It is deliberately careful about when it does this:

- **Only when it's worth it.** It first checks that the Podman machine holds
  at least about 1 GiB of reclaimable cache. If it doesn't, Windows is short of
  memory for some other reason and dropping the cache wouldn't help, so the
  worker leaves it alone and looks again about a minute later.
- **Not often.** At most one drop every 5 minutes, and never two at once.
- **Never during a build or a commit.** An image build or DevBox commit that
  the worker is running both creates that cache and is slowest without it, so
  the drop waits until it has finished; the worker checks again immediately
  before dropping. It can't see image pulls or builds you run yourself on the
  same Podman machine.
- **Checked afterwards.** After each drop it waits up to a minute for Windows'
  available memory to rise by at least 256 MiB. If it doesn't, or the drop
  command itself fails, the worker logs **one** warning and waits longer
  before trying again: 10 minutes, then 20, then 40, then at most an hour
  between attempts. It never gives up entirely, and a drop that works resets
  the wait.

The drop runs as root inside the Podman machine through `sudo`, and never waits
for a password. A standard Podman machine allows that; if yours asks for a
password, the drop fails and you get the warning above.

It is inactive everywhere a drop can't return memory to the host or can't be
run safely: Docker, a Hyper-V backend, macOS, Linux, a remote engine, and any
setup where the worker can't tell whether the engine is a local WSL machine.
The worker logs at startup whether it's `host memory reclaim active` or
`host memory reclaim inactive`, with the reason.

This is a safety net for the host, not a sizing input. The CLI still sizes the
runtime as if reclaim does not work until reclaim is
[verified](#verifying-it-works-on-your-machine), and a drop by the worker never
counts as a verdict.

Two environment variables control it. The worker reads them when it starts, so
set them in the environment you run `clustercode worker` from, then restart the
worker:

| Variable | Effect |
|---|---|
| `WORKER_HOST_RECLAIM` | `off` turns the automatic cache drop off; `false`, `0`, `no` and `disabled` do the same. Unset, or `on`, leaves it on. Any other value also turns it off, with a warning in the log. |
| `WORKER_HOST_RECLAIM_FLOOR_MB` | The floor, in MiB, below which Windows counts as short of memory. Default `4096`. Accepts a whole number from 1 to 1048576; anything else is ignored with a warning, and the default applies. |

A higher floor makes the worker act earlier, at the cost of dropping cache that
Windows could have lived with.

## What the scheduler sees

When the worker has verified that the container engine is a Podman machine on
this host whose memory Windows or macOS actually has to supply — the WSL backend
on Windows, or a local Podman machine on macOS — it advertises the smaller of
two figures: the memory the container runtime says is available, and the
memory the *host* itself says is available. The dashboard's Capacity panel
shows that smaller number, so a host under memory pressure is never handed
DevBoxes it cannot physically hold — even when the runtime's own accounting
still looks roomy. As reclaim, or the worker's own cache drop, returns memory
to the host, Free rises again and the worker's advertised capacity recovers
with it. If the worker can't confirm that — a remote engine, a Hyper-V machine,
or a setup it can't identify — this host cap isn't applied.

## The DevBox fit table

Because DevBoxes come in different sizes, a single "fits ~N DevBoxes" number
would hide how the count changes at other sizes. `onboard` prints a full
table before asking you to confirm a change:

```
  2 GiB (small)         fits ~10
  4 GiB (default)       fits ~5
  8 GiB (large)         fits ~2
  16 GiB (extra large)  fits ~1
Counts are per size — mixed sizes share the same pool.
Windows DevBoxes need ~2 GiB more than their size, so fewer fit than shown.
```

A few things worth understanding about this table:

- **Each count subtracts a host reserve first** —
  `max(2 GiB, 5% of the runtime memory)` — then divides what's left by that
  row's size. The table isn't simply "total ÷ size."
- **These are estimates**, not guarantees — the underlying accounting mirrors
  what the scheduler uses, but actual capacity depends on what's actually
  running.
- **Counts are per size**, not additive — a pool that "fits ~10 small" or
  "fits ~5 default" doesn't mean you get both at once; mixed sizes share the
  same pool.
- **Counts are nominal for Windows DevBoxes** — a Windows DevBox needs
  roughly 2 GiB more than its stated size to run, and the table does not
  subtract that. Treat "fits ~5" as an upper bound, not a promise of five
  Windows DevBoxes.
- **Budget one size up for a DevBox running a graphical session** — the exact
  overhead of a graphical session isn't precisely measured, so treat "one size
  up" as the working rule rather than a specific GiB figure.

## Changing it

Two ways to set it:

- **Interactively**, via [`clustercode onboard`](/cli/onboard) — asks
  dedicated-vs-shared (unless `--memory` is passed, which skips straight to
  the fit table), then still asks you to confirm before applying, since
  applying it restarts every WSL distribution on Windows.
- **Directly**, via [`clustercode config set RUNTIME_MEMORY_MB <mb>`](/cli/config#runtime_memory_mb)
  — validated, but only takes effect the next time a container-runtime
  machine is created or `onboard` runs; setting the key alone doesn't move
  memory around, and is deliberately not treated as consent to apply it
  unattended.

`clustercode onboard --memory <mb>` is the only way to apply a change
**non-interactively** (CI, scripts): without a terminal to confirm in, it
applies immediately rather than prompting. With a terminal attached, the same
flag still confirms before applying — it only skips the sizing questions.

After a successful apply, `onboard` records the value it applied as
[`RUNTIME_MEMORY_MB`](/cli/config#runtime_memory_mb). That's what tells
`doctor` the size was a deliberate choice rather than an install default, so it
stops suggesting a different one. And on a machine that is already the right
size, `onboard` still offers to turn memory reclaim on where it's off — that path changes no
allocation at all, and once the entry is written it offers to
[measure](#verifying-it-works-on-your-machine) whether it does anything, then
to raise the size if it does.

For Docker, `onboard` never applies the change at all, on any platform — see
below.

<Aside type="caution" title="Windows: applying this restarts every WSL distribution">
  On Windows, Podman's own memory controls don't work inside its WSL2 VM —
  `podman machine set --memory` errors, and `podman machine init --memory` is
  silently ignored. The actual control is the `[wsl2] memory=` setting in
  `%UserProfile%\.wslconfig`, which WSL applies to **every** distro on the
  machine, not just the one Podman uses.

  `clustercode onboard` edits this file for you — preserving comments and
  other keys, and keeping a one-time `.bak` copy — then runs `wsl --shutdown`
  to make it take effect. That command **restarts all of your WSL
  distributions**, so save any work in other WSL sessions before confirming
  the change. The same applies when only memory reclaim is being turned on:
  the `[experimental]` entry is read at VM start like every other key, so that
  change restarts every WSL distribution too, even though no allocation moves.
  WSL's own out-of-the-box default, before you configure anything, is roughly
  half of host RAM.
</Aside>

On macOS, `podman machine set --memory` works directly, but the machine must
be stopped first — `onboard` handles the stop/set/start sequence for you.

<Aside type="note" title="Docker: onboard tells you where to set it, but doesn't set it">
  With Docker as the engine, `onboard` doesn't apply a memory change on any
  platform — it only reports the current size and points you to where the
  setting lives:

  - **Windows, Docker Desktop's WSL2 backend** — `[wsl2] memory=` in
    `%UserProfile%\.wslconfig`, the same file described above. Docker
    Desktop's own memory slider is disabled in this mode, so changing it
    there does nothing.
  - **Windows, Docker Desktop's Hyper-V backend** — Docker Desktop's own
    Resources settings.
  - **macOS** — Docker Desktop's own Resources settings.

  Set the value yourself, then restart Docker (or, for the WSL2 backend, run
  `wsl --shutdown`, which stops every WSL distribution) for it to take effect.
  On the WSL2 backend `[experimental] autoMemoryReclaim` is yours to set by
  hand as well (from WSL 2.5.10 reclaim is on unless it says `disabled`).
  `doctor` reports whether it's on, but the CLI can't verify it for Docker, so
  size Docker as if reclaim does not work.
</Aside>
